## 0. 어떤 작업이든 먼저 지키는 것

**역할 분담(2026-09-12 확정).** 구현은 **Claude Code**, Claude(claude.ai)는 검토자·검증자·프롬프트 설계자, **삭제·라이브·자금 관련 변경은 Codex 독립 검토** 후 배포한다. (VCB 트랙은 Antigravity 구현이었음 — 저장소 CLAUDE.md가 명시하면 그것을 따른다.) 그래서 이 스킬의 산출물은 대개 "구현 에이전트에게 보낼 영문 프롬프트"이거나 "에이전트 보고에 대한 판정"이다. 프롬프트에는 결정·조건·게이트·회신 형식을 명시하고, 에이전트가 알아서 정하도록 남겨 두지 않는다.

**보고를 믿기 전에 대조한다.** 이 프로젝트들이 반복해서 겪은 실패는 "성공을 보고하지만 실제로 안 된 것"이다(`sent: true`인데 배달 0건, `|| true`가 실패를 삼킴, 프로세스는 active인데 스레드 사망, 죽은 상수, 대체값 가드가 분모를 바꿔치기). 에이전트가 "완료"라고 하면 그 근거(rc, 카운트 일치, 저널, md5)를 요구한다. 도구 출력은 verbatim으로 붙이게 하고, 재구성된 출력은 하드 실패로 본다.

**하드코딩 금지는 값에 대한 것이다.** tickSize·stepSize·MIN_NOTIONAL·MMR·수수료·펀딩 cap·브라켓을 코드 리터럴로 박으면 헌법 위반이다. 기동 시·주기적으로 인증 API에서 조회하거나 캡처 스냅샷에서 로드한다. 반대로 리스크 가버너의 *구조*(마진캡·킬스위치·stale-data kill)는 결정론적으로 하드코딩하는 것이 맞다 — 학습 대상이 아니다.

**결과를 본 뒤 규칙을 바꾸지 않는다.** 임계·게이트·보존일·창 길이는 사전확약이다. 사후 조정이 필요해 보이면 그것은 튜닝이 아니라 설계 변경이고, 레지스트리에 정정 행을 덧붙이고 Codex 검토를 거친다.

**한 문서가 정답이다.** 바이낸스 API는 단일 스펙이고 심볼별 차이는 반환 데이터값이다. 심볼별 별도 문서를 만들지 않는다(드리프트=룰 위반). 심볼별 표는 한 문서 안에 둔다.

## 1. 영역 A — 거래소 게임룰 (요약, 상세는 references/exchange-rules.md)

정본은 저장소의 `docs/바이낸스문서API_2026_v6.md`(이하 v6)다. v6는 "런타임 진리원"이 아니라 "검증된 참조 + 드리프트 감지 기준선"이다. 코드 리뷰 시 아래를 순서대로 확인한다.

1. **주문 정책** — 진입·청산 전부 `type=MARKET`. `side`는 `BUY`/`SELL`만(`LONG`/`SHORT` 절대 금지). 청산은 `reduceOnly="true"`. 원웨이 모드(`positionSide=BOTH` 생략 가능). 서버측 STOP/TP는 쓰지 않는다(2025-12 algoOrder 이관, 구 엔드포인트 -4120). SL/TP는 봇이 모니터링 후 MARKET reduceOnly로 청산한다.
2. **정규화 순서** — 수량은 stepSize로 *내림* → 내림 *후* `qty×price ≥ MIN_NOTIONAL` 재확인(내림이 명목을 하한 아래로 밀 수 있다) → 미달이면 한 step 올리거나 포기(추격 금지) → 가격은 tickSize 배수(Decimal 사용, float 나눗셈 금지). reduceOnly 청산은 MIN_NOTIONAL 면제. MARKET_LOT_SIZE의 maxQty가 시장가 1주문 상한이다.
3. **기동 게이트(B2)** — LIVE는 `positionRisk.marginType`을 확인하고 ISOLATED가 아니면 포지션·미체결 0 확인 후 전환, 재조회로 확정, 실패 시 기동 중단(청산만 허용). PAPER는 계정 SET 금지, WARNING만. 레버리지도 기동 시 명시 설정(미설정 시 계정 기본 5x·cross로 매매된다).
4. **maxNotionalValue 혼동 금지(B3)** — `positionRisk.maxNotionalValue`는 브라켓 `notionalCap`이 아니다. 사이징은 `/fapi/v1/leverageBracket` 런타임 조회를 쓴다.
5. **순간값은 기준선이 아니다(B1)** — markPrice/indexPrice/lastFundingRate/nextFundingTime은 시세다. 드리프트 하네스 비교 대상에서 제외.
6. **심볼별 값** — MIN_NOTIONAL(ETH 20/XRP 5/BTC 50), tick/step, 최대 레버(ETH 150/XRP 100), 펀딩 cap(BTC·ETH ±0.30%/XRP ±0.375%), liquidationFee(SOL만 1.5%)가 다르다. BTC 값을 다른 심볼에 차용하지 않는다. 미표기 심볼은 exchangeInfo/leverageBracket/fundingInfo 조회 필수.
7. **비용** — VIP0 maker 0.02%/taker 0.05%. 50~1,000 USDT 규모에서 마찰은 거의 전부 수수료(왕복 슬리피지 0.016 bps 실측, 2026-08 레짐 꼬리표). 단기 신호는 비용이 엣지를 먹는다 — 비용 차감 전 성과는 성과가 아니다.
8. **청산 데이터** — `@forceOrder` 스트림은 심볼당 1초 창에 *가장 큰* 1건만 푸시하는 스냅샷이다(공식문서 "latest"→"largest"변경). 청산 *총량* 지표로 쓰면 안 된다. 무료 과거 아카이브 없음(binance.vision 부재) → 전향 수집 또는 Tardis(Tardis도 초당 1~2건 천장 — 대조는 수집 충실도).
9. **웹소켓 티어(2026-04-23 이후)** — 레거시 `/ws`·`/stream`은 `/public` 티어(trade·bookTicker·depth)만 전달하고 `/market` 티어(aggTrade·markPrice·kline·forceOrder)는 **구독을 수락한 뒤 조용히 0건**이다. 티어별로 소켓을 나누고(`/public/ws`, `/market/ws`, `/private/ws`), 0건 결론의 대조군은 같은 소켓이 아니라 **같은 티어**로 잡는다. 2026-09-12 E2E에서 이걸 몰라 forceOrder "미전달"로 오판했고 markPrice REST 폴백이 원인을 3개월간 가리고 있었다.

## 2. 영역 B — 연구 규율 (요약, 상세는 references/research-protocol.md)

- **사전등록 → 측정 → 3분류 판정(ACCEPT/REJECT/폐기) → 인간 승인.** 가설·게이트·OOS 앵커·N 카운터를 측정 전에 확정한다. 앵커 시각 증거는 Drive createdTime(modifiedTime은 보조, 로컬 mtime은 다운로드 시각이라 절대 대용 금지).
- **게이트 순서** G0(이벤트 수) → G1(총 엣지) → G2(비용 차감 순 엣지) → G3(OOS) → G-B(PSR/DSR + 다중검정 보정) → 벤치마크 비교. 성과 조건에서 트레이드 0건 = 즉시 FAIL. PSR>0.5와 n≥30은 별개 필수조건. 단일자산 6년 표본에서 t≥3은 구조적으로 불가능하므로 PSR/DSR+벤치마크가 올바른 설계다.
- **플라시보 3층** 무작위 타이밍 부트스트랩·신호 지연·부호 반전. 플라시보가 신호를 지배하면 기각.
- **레지스트리는 append-only.** 틀린 행은 고치지 않고 정정 행을 덧붙인다. 실패 후보의 이름만 바꿔 재제안하지 않는다(레지스트리 대조).
- **정직한 기각도 성과다.** 검정력 부족(MDE≫임계)과 효과 부재(MDE≪임계)를 구분해 보고한다.
- **격리 실행 하네스** — 정본 전략 코드를 subprocess로 그대로 돌린다. 측정용 재구현 금지.
- **스코프 드리프트 경계** — 성공 정의는 "진짜 알파 발견"이지 "인프라가 잘 돈다"가 아니다. 인프라 검증으로 흘러가면 그것을 명시적으로 지적한다.
- **이미 기각된 것**(learnings): 30분 이하 단기 신호는 비용이 엣지 대부분을 먹음 / 분위수 조건 AND 결합은 표본을 파괴 / VPIN은 방향 신호가 아님 / SL 클리핑 사이징(v1)은 기각, 레버리지는 SL 거리에서 도출 / ATR 스케일은 실행 스케일과 일치해야 함 / 돈치안 돌파 메타라벨·변동성 레짐·스프레드 base signal 전부 REJECT(E2E Phase 1~2a). 새 트라이얼 설계 시 이 목록과 대조하고, 겹치면 무엇이 다른지 먼저 답하게 한다.

## 3. 영역 C — VPS 운영 (요약, 상세는 references/vps-ops.md)

- **원천 최고 해상도로 수집한다.** 매매봉(1m)은 의사결정 주기지 수집 주기가 아니다. 공백·재연결·시계 드리프트는 manifest에 기록하고 일별 quality가 게이트를 판정한다. **L2는 소급 구매가 불가능하다** — 수집 중단은 영구 결손이다.
- **prune ↔ reconcile ↔ drive-verify는 상보적 설계다.** 보존 30일과 대사 30일 창은 의도적으로 맞춘 것이라 한쪽만 바꾸면 설계 변경이다. Drive 검증(md5) 통과분만 로컬 삭제하고, prune된 날짜는 Drive가 유일본이므로 verify가 그 존재를 계속 확인해야 한다.
- **대칭 구멍은 한 곳에 있지 않다.** store를 늘릴 때는 prune만 넓히지 말고 reconcile·drive-verify·grouping·adopt를 *먼저* 같은 범위로 넓힌다. 검사가 안 넓어진 채 삭제만 넓어지면 검증 0인 유일본이 생긴다. 삭제 코드는 allowlist(`deletion_mode`)로 뒤집고, 검사 확장 → 무삭제 1주기 관측 → dry-run → 실삭제 순으로 간다.
- **파생물은 `pruned`가 아니다.** raw에서 재생성 가능한 파생 데이터는 별도 짧은 보존 정책이고 대장 상태도 별도(`expired_local_derivative`). `pruned`는 "Drive가 유일본"이라는 뜻이라 원격 사본 없는 것에 쓰면 거짓 상태다.
- **예보는 증가하는 것 전부를 재야 한다.** 한 store만 재는 disk_days_left는 우연히 맞을 뿐이다. 두 봇이 같은 인스턴스면 `du -sh`로 각각의 증가율을 분리해 둔다.
- **디스크가 차기 전엔 늘리는 게 먼저다.** EBS 온라인 확장은 아무것도 지우지 않고 수집을 안 멈추며 월 몇 달러다. 지우는 정책 정리는 그 뒤에 여유 있게 한다. 절차와 주의사항은 references/vps-ops.md §EBS.
- **SSH 키가 공유되면 호스트를 먼저 확인한다.** 파티션·파일시스템 명령 전에 `hostname`·`lsblk`를 보여주게 하고 콘솔에서 바꾼 볼륨과 일치하는지 사용자가 확인한 뒤 실행한다.
- **알림은 발화 조건이 설계의 절반이다.** 상시 발화하는 경보는 사람이 끄고 결국 침묵을 만든다. 반복형은 스로틀, 확정 사실은 하루 1통. 스로틀 키가 매일 바뀌는 구현은 무한 발송이다.

## 3-1. 영역 D — 전략 모듈 (요약, 상세는 references/strategy-modules.md)

사용자 확정(2026-09-12): 대상 **BTCUSDT**, 레버리지 **50~100x 레짐별 동적**, 메인 **1m 봉**, **페이퍼 1개월(도쿄 VPS) 후 사용자 만족 시 라이브**, 텔레그램 강제청산은 **ID 화이트리스트 + 예/아니오 확인 + 3초 간격 3회 재알림, 무응답 시 취소**. 이 전제에서 스킬이 강제하는 것:
- 레버리지는 레짐 라벨로 고르지 않는다. **SL 거리 → 레버리지 도출 → 50~100x로 클램프 → SL×버퍼 < 청산 거리 검사** 순서이고, 검사를 못 넘으면 레버리지를 낮추거나 진입하지 않는다. 100x·MMR 0.4%의 청산 거리는 0.6%다.
- 1m은 의사결정 주기다. 상위 스케일 컨텍스트를 1m에서 평가하는 구조를 권장하고, "30분 이하 신호는 비용이 엣지를 먹는다"는 기각 발견과 G2 비용 게이트는 면제되지 않는다.
- 평가지표는 **판정용 7개**(순수익률·n/n_eff·PSR/DSR·MDD·PF·청산/킬스위치 횟수·벤치마크)만 사전등록하고, 나머지(Sharpe·Sortino·Calmar·Omega·Ulcer·Martin·VaR/CVaR·회복기간·승률·R:R·노출·Monte Carlo·R²·IR·t/p)는 quantstats 진단 티어시트로 판정 뒤에만 본다.
- 피라미딩·트레일링·부분익절은 각각 config 플래그, 전부 봇 모니터링 + MARKET(청산 reduceOnly). 추가·부분청산 후 청산 거리 검사와 MIN_NOTIONAL을 매번 재실행.
- 지지/저항은 결정론적 정의(fractal·피벗·돈치안·볼륨 프로파일·KDE·레벨 강도)만 쓰고 파라미터·계산값을 DB에 남긴다. 예측력 자체가 가설이라 플라시보와 비교한다.
- DB는 판단 시점 값을 저장한다: bars·features_base/adv/custom(params_version)·decisions(거부 사유 포함)·orders(원문 JSON)·positions·runtime_rules 스냅샷.
- 라이브 전환의 "사용자 만족"에 최소 객관 조건을 붙인다: 1개월 킬스위치·청산 0회, 대사 불일치 0건, 비용 차감 후 순손익 보고, 전환 체크리스트 전부 통과.

## 4. 구현 에이전트 프롬프트를 쓸 때

영문으로 쓴다(에이전트는 영문 지시에 더 정확하다). 아래 형식을 기본으로 하고 사안에 맞게 줄인다.

```
[Context / decision in one or two lines]

## Decisions
1. ...  (사용자가 결정한 것 — 에이전트가 재판단하지 않게 명시)

## Gates — do not skip
- Stage X → Y: [무엇을 보여줘야 다음으로 가는지: rc, 카운트, 저널, dry-run 수치]
- Any deletion / live-order / collector change: dry-run or diff first, user confirms.

## Registry
Append a row: [승인·조건·근거·검토자]

## Reply with
[해시, 삽입된 행 문안, 설계 문서 경로, 측정치 — 체크 가능한 것만]
```

프롬프트에 넣어야 할 상수 조건: 실주문 경로가 금지된 저장소(E2E)에서는 `create_order` 계열 구현 자체를 금지한다는 것, 삭제·라이브·수집기 변경은 Codex 검토 후라는 것, 결과 본 뒤 임계 수정 금지라는 것.

## 5. 설계서·CLAUDE.md·스킬을 새로 쓰거나 개정할 때

먼저 `references/open-decisions.md`를 연다. 레버리지·메인 분봉·라이브 전환·대상 심볼·텔레그램 안전장치·구현 도구 역할은 2026-09-12에 확정됐고 그 결정에 따라오는 제약이 같은 표에 있다. 새로 생기는 충돌은 같은 표에 "미결"로 추가하고 임의로 한쪽을 고르지 않는다. 사용자에게 확인할 것이 있으면 문서를 완성하기 전에 묻는다(기본환경설정 원칙 13).

새 문서는 v6의 위상 규칙을 따른다: 문서는 참조·기준선이고 값은 런타임이 진리원이며, 값 신뢰도를 `[DOC]`/`[LIVE-ONLY]`/`[DERIVED]`로 표기한다.
