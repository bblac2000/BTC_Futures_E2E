## 0. 목적과 한계
- 스크린은 정식 사전등록 **앞의** 값싼 1단계 깔때기다. "이 가족을 정식 트라이얼로 올릴 가치가 있는가"만 가른다.
- **스크린 결과는 매매의 근거가 아니며 그렇게 인용할 수 없다.** PASS는 "사전등록 초안을 써 볼 만하다"는 뜻이고, 그 이상이 아니다.
- 스크린 코드는 `research/screens/` 아래에만 둔다. 봇·주문 경로가 없다(`create_order`류 호출 0 — 시험이 강제). 헌법 v1.6 병합 전에는 실주문·페이퍼 주문이 0이다(P0의 대조군 포함).

## 1. 두 원장 (D2)
1. **정식 트라이얼 카운터 N**은 정식 IS 판정으로만 오른다. 스크린은 N을 건드리지 않는다. 이번 라운드는 정식 트라이얼이 없으므로 N을 쓰지도 바꾸지도 않는다(교차 저장소 값의 감사는 `docs/n_counter_audit.md` · 값의 확정은 첫 정식 사전등록 때 사용자).
2. **스크린 원장** `docs/screen_registry.md`(append-only)에는 두 종류의 기록이 있다.
   - **S 행(알파 스크린)**: id `S-1, S-2, …`. 가족의 k에 들어간다.
   - **M 행(측정)**: id `M-1, …`. 알파 가설이 아닌 계측(P0 실행 감사)이다. **어떤 가족의 k에도, N에도 들어가지 않는다.** 대신 실행 전에 킬 문턱을 고정한다(§3-3).
3. **두 단계 기록**: 스크린은 자료를 읽기 **전에** START 행(id · 날짜 · 가족 · 가설 · 스펙 SHA256 · 프로토콜 SHA256 · 코드 커밋)을 덧붙여 커밋한다. 끝나면 같은 id의 RESULT 행을 덧붙인다. 아무것도 덮어쓰지 않는다.
4. **가족**은 넷으로 고정한다: `execution` · `carry` · `xs-carry`(횡단면 캐리) · `directional`. START 행에 적은 가족은 바꾸거나 쪼갤 수 없다.
5. **k** = 그 가족에서 START 행을 가진 서로 다른 S id의 수 — FAIL · 판정 불능 · 자료를 본 뒤 중단한 것까지 전부.
6. **새 id 규칙**: 매개변수나 측정 의미(통계 · 표본 구성 · 추정량 · 귀무 · 비용 숫자 · 시드 · 창)를 **하나라도** 바꾸면 새 S id와 새 START 행이다. 의미를 바꾸지 않는 결함 수정은 결과를 보기 전이면 같은 id에 주석으로 남길 수 있다. 결과가 이미 있으면, 숫자를 바꾸는 수정은 새 S id다. 한 id = 한 변형 = 한 시드.
7. **승격**(스크린 가족 → 정식 트라이얼)은 사용자 결정이다. 승격 사전등록은 (a) 그 가족의 **전체 탐색 계보** — 이 원장의 그 가족 S id 전부(모든 결과)와 `~/project`의 다른 저장소에서 같은 가설 가족으로 돌린 정식·비공식 실행 전부 — 를 출처 경로와 함께 나열하고 (b) k가 DSR 수축에 **어떻게** 들어가는지를 감사된 정식 카운터와 나란히 명시·검증해야 한다(이중 계상 금지 · `backtest/stats.expected_max_sr`는 n_trials < 2를 거부한다). **그 명시가 있기 전에는 승격이 차단된다.** 이 문서는 그 식을 정하지 않는다.
8. Codex POST 검토가 MERGE여도 승격이 아니다. 원장의 `protocol review` 열과 `promoted?` 열은 따로다(§5).

## 2. 정식 판정기는 그대로다
이 문서는 정식 판정기의 어떤 값도 바꾸지 않는다. 현재 구현(`backtest/verdict_t4.py` · 사전등록 r3 §7-2):
- θ = **10 bps** · 검정력 부족: MDE > 2θ = **20 bps** · 효과 부재: MDE < 0.5θ = 5 bps ∧ 순 CI 상한 < θ = 10 bps · 부호 우선(순 CI 전부 0 아래 → 효과 부재(음의 효과)).
- MDE = (z₁₋α + z₀.₈₀) · sd / √n_eff · n_eff = n / (1 + 4 · max(ρ̂, 0.15))("n / 1.6"은 바닥이 걸릴 때만) · 계수 **3.340은 과거 값**(N = 8 · α = 0.05/8 · 검정력 0.80).
- 스크린이 적는 MDE는 **보고 전용**이며 단위·가정·검정력 목표를 함께 적는다. IC의 MDE는 bps 문턱과 비교하지 않는다. 앞으로의 계수는 감사된 N과 승인된 α 규칙에서 나온다(사용자가 첫 정식 사전등록에서 확정).
- 레지스트리 #88의 정식 트라이얼용 앵커 전 검정력 관문은 그대로 유효하다.
- 사용자 프롬프트의 "θ = 20 bps"는 위 **20 bps MDE 문턱(= 2θ)** 으로 읽어 기록했다 — 이 읽기의 확정은 사용자 결정 목록에 있다(레지스트리 #96).

## 3. 통과 규칙 (D3 · 고정)
### 3-1. 기본 규칙(알파 스크린)
**PASS = (가) 무비용 평균 ≥ 1.5 × 모형 왕복 비용 ∧ (나) 원래 통계가 귀무 분포의 p95 밖. 그 밖은 FAIL.**
- **같음의 처리(둘이 다르다)**: (가)는 `≥` — 평균이 1.5 × 비용과 **같으면 충족**. (나)는 엄격한 `>` — 원래 통계가 귀무 p95와 **같으면 미충족**.
- (나)의 "플라시보"는 **가설의 귀무(효과 없음)를 만드는 구성**이어야 한다. 견고성 점검(예: 캐리의 무작위 진입일)은 보고만 하고 통과 판정에 쓰지 않는다.
- 귀무 추출 수 = **1,000** · 시드는 스펙에 하나 · 시드를 골라 쓰지 않는다 · 실패 추출의 처리는 스펙에.
- 꼬리: `carry` = 한쪽 위(통계 > 귀무 p95 · 엄격) · `xs-carry`(IC) = **사전에 적은 방향 하나만**, 그 방향의 부호 있는 IC를 그 방향 귀무 p95와 한쪽 비교(음의 IC가 나와도 방향을 뒤집을 수 없다 · 양쪽 검정은 다른 S id) · `directional` = 한쪽 위.
- 분위 보간 = 선형(numpy 기본) · 통계나 귀무 분포가 정의되지 않으면 FAIL · 여러 통계를 묶어 판정하지 않는다(스펙이 미리 정한 하나).
- 벤치마크(§6)는 **보고 열**이지 통과 조건이 아니다. 스펙이 추가 보고 조건(예: 최근 하위 구간)을 둘 수 있으나, 그것으로 FAIL을 PASS로 바꾸지 못한다.
- 결과를 본 뒤 문턱 수정 없음.

### 3-2. 실행 차단
스펙에 **UNRESOLVED** 항목이 하나라도 있으면 그 스크린은 자료를 읽을 수 없다. "스펙에서 정한다"는 "실행 전에 정해 커밋한다"는 뜻이지 탐색 뒤에 고른다는 뜻이 아니다. 지금 UNRESOLVED이고 **사용자가 정할 것**:
- **P1(캐리)의 통과 귀무**: 가설 귀무 검정 하나를 지정해야 한다. 무작위 진입일 플라시보는 견고성 보고다. 부트스트랩 CI 기준은 "귀무 p95 밖"과 같은 것이 아니므로 대체하려면 명시적 사용자 결정이 필요하다.
- **P2(횡단면 IC)의 (가) 조항 대응**: IC는 무차원이라 "1.5 × 왕복 비용"과 비교할 대상이 없다. 사용자가 승인한 대응 또는 명시적 예외가 있어야 하며, 선언하지 않은 포트폴리오 가정을 들여오면 안 된다.

### 3-3. P0(실행 감사)는 통과 규칙이 아니라 킬 규칙
- **킬(고정)**: 최선의 T에서 폴백 비용을 포함한 순 개선이 **편도 2 bps 미만이면 "stay taker"** — 기록하고 P0를 끝낸다.
- 스펙이 실행 전에 고정할 것: "편도 순 개선"의 정의(결정 시각별 짝 비교 · 미체결은 테이커 폴백으로 처리해 포함 · 메이커/테이커 수수료 포함 · 역선택은 실현 체결가·폴백가로 포함 · 분모 = 표본의 모든 결정(체결분만이 아님)) · 후보 T 집합 {30, 60, 120}초 · "최선의 T" 선택 통계(공통 결정 표본에서 편도 순 개선의 평균) · 동률이면 작은 T · T를 관측 뒤에 더하면 새 M id.
- 체결 규칙에 "가격 닿음 = 체결"을 쓰지 않는다.

### 3-4. 스펙이 실행 전에 고정해야 하는 것(전 가족 공통)
`research/screens/<id>_spec.md`를 실행 전에 커밋하고 SHA256을 START 행에 적는다. 빠짐없이:
1. 표본 구성 — 유니버스 · 적격 · 제외 · 결손 처리 · 에피소드 닻 · 겹침 처리 · 주 경계 · **결과 구간 전체**(§4-3).
2. 추정량 — 가중 · 분모 · 정규화 · 펀딩/베이시스 회계. IC면 순위 규약 · 동률 · 예측 구간 · 방향 · 주 간 집계.
3. 귀무 생성 — 재표본 단위 · 블록/의존 처리 · 복원 여부 · 위험 정합 · 시드 · 실패 추출 처리.
4. 결정 계산 — **스펙은 §3-1~§3-3의 고정 규칙(부등호 · 꼬리 · p95 · 1.5배 · 추출 수 · 킬 문턱)을 바꾸거나 느슨하게 할 수 없다.** 스펙이 하는 일은 이 문서가 비워 둔 세부(통계의 정의 · 귀무의 구성 · 시드 등)를 채우는 것뿐이다. 충돌하면 이 문서가 이긴다.
5. 비용 모형(측정된 값 · 출처) · 벤치마크 방법(§6) · 가장 가까운 기각 트라이얼과 차이.

## 4. 자료 창과 예약 구간 (D4)
### 4-1. 창
스크린은 **2021-01-01 00:00:00.000Z → 2026-06-30 23:59:59.999Z**만 읽는다. **2026-07-01부터는 예약 구간**이며 알파 스크린이 읽을 수 없다(승격되는 가족의 전진/OOS 예비).

### 4-2. 코드로 집행
- `research/screens/window.py`: `require_window`(I/O **전** 범위 검사 · 우회 인자 없음) · `refuse_reserved_archive`(2026-06 뒤의 달을 가리키는 아카이브는 열기 전에 거부) · `assert_within`(계산 직전 검사) · 읽기 경로 셋 — `bounded_csv_file` · `bounded_zip_csv`(파일을 **가드 모듈이** 열고 줄마다 시각 칸만 잘라 본 뒤 창 안의 줄만 호출자의 `parse`에 넘긴다 · 창 밖 줄은 해석 없이 버리고 센다 · 잘못된 시각은 예외) · `fetch_json_rows`(공개 GET을 가드 모듈이 직접 부르고 응답 행의 시각을 먼저 검사한다 · 창 밖 행이 하나라도 있으면 어떤 행도 넘기지 않고 예외) · zip의 머리줄 유무는 자동 판별하지 않고 `zip_has_header`(시각 칸만 본다)의 답을 명시해 넘긴다 · `write_result`(결과를 한 번만 쓴다).
- `research/screens/p1` · `p2`의 시장 자료 읽기는 각 가족의 `loader.py` 하나에서만, 위 읽기 경로로만 한다. 이 두 디렉터리의 모듈은 **허용 목록**의 import만 쓴다(순수 계산용 표준 모듈 · numpy · 같은 가족 패키지 · `window`의 공개 이름 `window.PUBLIC`만 · `loader.py`는 `pathlib.Path` 추가). 직접 읽기·동적 접근 이름(`open` · `read` · `load` · `getattr` · `io` …)은 이름으로도 속성으로도 쓸 수 없다. 기존 계층(`backtest` · `strategies` · `paper` · `exchange` …)과 `p0` · 다른 가족을 import하지 않는다.
- 정적 규칙은 **심층 방어**다 — 모든 우회를 막는다고 주장하지 않는다. 스크린마다의 스펙 PRE·결과 POST 검토(§7)가 코드의 읽기 경로를 다시 본다.
- 시험 `tests/test_screen_window.py`가 강제한다: 2026-07-01에 닿는 요청 거부 · 실제 파일·zip 읽기 경로에서 예약 구간 값이 한 번도 해석되지 않음 · 7월 이름 파일은 열기 전에 거부 · 잘못된 시각은 건너뛰지 않고 예외 · 정적 규칙(알려진 우회의 회귀 사례 포함) · API 응답은 창 밖 행이 있으면 한 행도 해석되지 않음 · 결과 파일은 배타 생성 · 주문 경로 문자열 없음.
- 정식 트라이얼이 예약 구간을 읽게 하려면 **코드 변경 + 레지스트리 행**이 필요하다(이번 라운드에는 그런 경로가 없다).

### 4-3. 글로 정하는 규칙(코드 검사에 더해)
- **결과 구간도 창 안**: 진입이 6월이어도 30일 보유나 다음 주 수익률이 7월 자료를 필요로 하면 그 관측은 표본에서 뺀다.
- 모든 의존 자료(벤치마크 계열 · 대조군 · 유니버스)가 같은 가드를 지난다. 예약 구간 관측으로 만든 캐시·집계를 쓰지 않는다. 유니버스 선정에 예약 구간 정보를 쓰지 않는다. 경계를 넘는 전 구간 정규화·보간을 하지 않는다.
- 각 RESULT 행은 **실제로 읽은 자료 범위**(첫/마지막 시각)와 입력 목록의 해시를 적는다. 다만 최소·최대 시각만으로는 파생 입력이 예약 구간을 배제했음을 증명하지 못하므로 입력 목록(파일 · SHA256)을 함께 고정한다.

### 4-4. 하나뿐인 예외 — P0 실행 계측
> 2026-07-01 이후는 알파 스크린의 접근이 막힌 예약 구간이며, 실행 계측 예외가 하나 있다: P0를 위한 수집기 자료 **2026-09-17 → 2026-10-11**. 이 파일럿 구간은 **노출된 실행 개발 자료**다. P0 자신에게도, 설계·선택·실행 모형이 P0에 의존하는 승격 가족에게도 손대지 않은 OOS가 될 수 없다. 승격은 이 노출을 공시하고, 필요한 엠바고와 함께 겹치지 않는 평가 구간을 사전등록해야 한다. 다른 예약 날짜는 의존성 감사 뒤에만 쓸 수 있다.
- P0 로더는 `research/screens/p0/`에만 있고 위 범위를 상수로 박으며 수집기 파일만 읽는다. 신호·수익률을 계산하지 않는다.
- **보조 구간(사용자 결정 2026-10-14 답변 3 원문: "The 07-24 → 09-16 span (depth/bookTicker only) may feed a 'touch frequency' auxiliary column only — never the fill decision and never the conclusion.")**: 수집기 자료 2026-07-24 → 2026-09-16은 "닿음 빈도" 보조 열에만 쓸 수 있다. 이 구간도 **같은 노출 규칙**을 따른다 — 읽는 순간 노출된 실행 개발 자료가 되며 위 인용문의 제한(OOS 불가 · 승격 시 공시 · 겹치지 않는 평가 구간)이 그대로 적용된다. P0 스펙이 이 열을 쓰지 않기로 하면 이 구간은 읽지 않는다.
- 따라서 P0가 노출할 수 있는 예약 구간의 합은 2026-07-24 → 2026-10-11이고, 그 밖의 예약 날짜(2026-07-01 → 07-23 · 2026-10-12 →)는 P0가 읽지 않는다.
- 스크린으로 본 날짜(2021-01 → 2026-06)도 승격되는 가족에게는 개발 자료다. 로더 가드가 통과해도, 연구자가 이미 본 정보로부터의 독립을 보장하지는 않는다.
